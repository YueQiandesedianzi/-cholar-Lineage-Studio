# Git 式协作约定

## 提交（commit）

- **原子化**：一次提交 = 一类变更（新增证据卡片 / 撰写章节 / 核验结果）。
- **附说明**：message 说明"谁 / 何时 / 改了什么 / 为什么"。
- **可回溯**：每次提交记录作者、时间、差异，历史不可破坏（回滚 = 新提交，非删除）。

## 审核（review）

- **内联评论**：定位到具体卡片或段落，不写笼统意见。
- **阻断**：`要求修改` 状态阻断合并，直到作者更新并重新提交。
- **批准门槛**：合并前满足约定批准人数（默认 ≥1 人批准）。

## 合并（merge）

- **冲突判定**：同一卡片/段落被多个分支修改且结果不同 → 冲突。
- **解决方式**：保留主干 / 保留分支 / 手动合并，三选一并记录。
- **不静默改写**：冲突解决本身是一条受审的记录。

## 版本（tag）

- 关键节点打标签（`v1.0`、`v1.1`），可回溯任意版本。
- 合并前做**证据追溯校验**（见 SKILL.md 步骤 7）。

## Web 实现（ChangeUnit）

`web/collaboration.py` 将上述约定落到 SQLite：分支/提交/审核/冲突/标签/回滚均有 API 与追加式审计，不依赖 Git 命令。默认至少一位非 MR 作者的审核人批准；源分支的新提交会使旧批准不适用于新 head。冲突保留旧记录，必须解决当前活动冲突后才能合并。

接口、三选一语义、快照格式和限制见根目录 `README.md`；回归测试见 `web/tests/`。本地原型没有认证，作者字段只用于留痕。首次协作初始化之后，旧的导入/核验等兼容接口仍直接作用于 main 活动表，并不自动生成提交。

## 模拟日志格式

使用 `assets/division-of-labor-log-template.md` 记录：团队角色表、提交时间线、内联评论、合并冲突、追溯校验、最终产物清单。
